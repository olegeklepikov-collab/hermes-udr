# Hermes Foundation Bridge

## Поколения текстового индекса

`foundation_index_rebuild` сохраняет прежний режим восстановления пустой коллекции. Необязательная пара `generation_action` и `generation_id` включает новый режим: `replace` строит отдельную коллекцию из принятого исходного журнала, проверяет её обратным чтением и атомарно меняет `zvec/active-generation.json`. Старые коллекции сохраняются. `rollback` допускает возврат только к непосредственно предшествующему поколению и только если исходный журнал и отметки удаления с тех пор не изменились. Поля `expected_document_count`, `expected_active_count`, `apply` и `schema_version` остаются обязательными.

Пример замены: `{"schema_version":1,"apply":true,"expected_document_count":100,"expected_active_count":95,"generation_action":"replace","generation_id":"G-2"}`. Для отката передайте `generation_action="rollback"` и идентификатор из `previous_generation_id` квитанции. Новые записи после переключения делают старый откат недопустимым: нужно перестроение нового поколения по текущему журналу, а не потеря записей ради возврата версии.

Читатели выбирают одну готовую коллекцию; `collection_ref` в квитанции запроса показывает фактически выбранный путь. Обрыв до переключения оставляет прежний индекс доступным, после переключения — новый. Незавершённые или невыбранные поколения не удаляются автоматически. При неудавшемся построении повтор выполняется с новым идентификатором; уже выбранное поколение допускает идемпотентное подтверждение, пока журнал не изменён.

Поддерживается только существующий FTS/BM25-профиль с `embedding_model=none`, `dimension=0`. Несовпадающий манифест отклоняется. Смена моделей векторных представлений и переход между ненулевыми размерностями здесь не реализованы.

## Очередь событий

Обработчики событий сохраняют метаданные в `hook_queue` существующего `observability/collector.sqlite3`, затем применяют не более двух записей к координатору. Ожидание каждой блокировки SQLite ограничено 50 мс. В очереди не сохраняются исходный результат инструмента, текст фрагмента и поисковый запрос. Она входит в резервную копию базы наблюдаемости; отдельного хранилища резервирования не требуется.

Если приём локальной записи встретил временную блокировку SQLite, выполняются не более трёх попыток. Одинаковый отпечаток записи предотвращает дублирование. Другие ошибки и внешние действия так не повторяются. Совокупное ожидание приёма может достигать 150 мс плюс время файловой системы; при длительной недоступности остаётся явное предупреждение о незавершённом сохранении.

Для обновления повторно выполните `foundation_observability_migrate` с `apply=true` либо общую миграцию основания. Миграция добавляет таблицу без удаления старых данных. `foundation_trace_health` показывает ожидающие и изолированные конфликтные события; при их наличии состояние `degraded`. `foundation_trace_reconcile` обрабатывает не более двух ожидающих событий за вызов и возвращает остаток в `hook_reconciliation`; следующие события жизненного цикла также продолжают обработку.

Предел очереди — 1000 неподтверждённых или конфликтных записей, предел одной записи — 64 КиБ. При заполнении сначала предпринимается ограниченная обработка старых событий; если места нет, новое событие не считается сохранённым и выводится `foundation_hook_not_fully_persisted` без содержимого события. При недоступности обеих баз сохранность нового события не гарантируется. Невалидный фрагмент и результат инструмента свыше 1 048 576 символов не разбираются в обработчике: появляется `foundation_fragment_registration_incomplete`, исходный результат остаётся в Hermes. Это ограничение служебной регистрации, не предел чтения источника исследовательским модулем.

Повтор после обрыва между записью координатора и подтверждением очереди идемпотентен. Конфликты остаются в очереди со статусом `quarantined`; они не удаляются автоматически и не превращаются в подтверждённые данные. Приведённые пределы не гарантируют полное время обработки при задержках файловой системы и не заменяют измерение нагрузки конкретного стенда.

## Совместимость повторной доставки

В версии 0.13.0b1 `foundation_delivery_redeliver` возвращает `RedeliveryAuthorizationReceipt` со статусом `redelivery_authorized`, а не подтверждение доставки. Неизвестный исход в журнале остаётся `ambiguous_delivery`; разрешение не отправляет сообщение и не увеличивает число наблюдённых попыток. Фактический транспорт должен отдельно выполнить разрешённую отправку и представить результат через `foundation_delivery_reconcile`. Противоречивое сочетание `provider_status=delivered` и `provider_accepted=false` отклоняется. При переходе с 0.11.0 потребитель должен обработать новый вид квитанции; старый статус `delivered_duplicate` сам по себе не доказывает транспортную отправку.

Отдельный новый пакет интеграции Hermes 0.21.3 с основанием Knowledge Work. Он использует только публичные механизмы регистрации инструментов и событий жизненного цикла, не импортирует внутренние модули Hermes и не запускает второй агентный цикл.

Версия 0.13.0b1 содержит 64 операции и пять событий жизненного цикла. Подпись и точный коммит проверяются по отдельной квитанции выпуска; наличие кода не является признаком производственной готовности.

- DoltStateAdapter для начальной локальной подготовки четырёх баз; при наличии точного манифеста полномочий DoltSQLAdapter переводит их предметные записи на закрытый сервер 127.0.0.1, отдельного писателя с непустым секретом, параметризованный CAS, `DOLT_COMMIT` и независимое обратное чтение. Работающий только через встроенный CLI режим не закрывает производственный G1;

- AgentMemory 0.9.29 с iii-engine 0.11.2 в отдельном контейнере, собственным `HOME`, двумя новыми томами и без опубликованных портов; сохранение, поиск, контекст и перезапуск привязаны к `tenant/project/profile/work_kind` через isolated `agentId`;
- Beads 1.1.0 в отдельной пустой Dolt-базе с префиксом `KWF`: bridge использует только публичные CLI-операции create/read/claim/close, не выдаёт SQL и не отождествляет `closed` с приёмкой;
- автоматическую регистрацию типизированного `foundation_fragment` после вызова инструмента и отдельное продвижение через контракт `hermes-research-report`;
- кросс-хранилищную сверку через публичный договор research-report.
- проверку выпуска по встроенному открытому ключу Minisign: подпись архива, точный 40-символьный коммит, чистое дерево исходников, состав архива, SHA-256 каждого файла и Apache-2.0.
- восемь раздельных профильных договоров Hermes, полную передачу результата, слепую первую позицию reviewer, операторский эффект без изменения основания, возобновление без повтора эффекта и независимое решение о слиянии;
- Telegram-договор с разрешённым DM polling, хешированными привязками session/project/run/bead/profile, карантином file/audio, отдельными хешами audio/transcript, состоянием `ambiguous_delivery` и повторной доставкой тех же байтов без повторного запуска модели.
- приватный локальный приёмник TraceEnvelope без сетевого интерфейса: содержательные поля не сохраняются, чувствительные атрибуты удаляются, P0/unknown/blocked не отбрасываются, а отказ приёмника переводит запись в ограниченный журнал с TTL.
- двенадцатиклассный договор учёта зашифрованных копий и восстановления, проверку хэшей файлов в альтернативном корне и независимые пределы RPO/RTO. Эти проверки сами по себе не подтверждают семантическое восстановление сервисов и не разрешают производственную активацию.
- закрытую подготовку прав SQL и контроля ветвей Dolt; администратора и служебного писателя разделяют разные секреты, а отсутствие SQL-службы является блокирующим состоянием основания.
- проверку единого идентификатора снимка, ограниченного окна заморозки, исходных последовательностей и отдельных RPO/RTO по всем 12 классам. Даже формально полный набор переданных квитанций остаётся кандидатом до независимого испытания служб.

Квитанция разрешения повторной доставки содержит дополнительное поле `user_notice`: предупреждение о возможном повторе, полный SHA-256 прежних байтов и явное отсутствие подтверждения отправки и получения. Транспорт должен показать этот текст пользователю; наличие поля само по себе не удостоверяет отображение в Telegram. Изменение добавляет поле выхода, не меняя входной запрос или состояние доставки.

## Внешние операции и утраченные ответы

Перед записью памяти, записью факта графа и удалением связей артефакта мост сохраняет начало операции в существующей таблице `runtime/runtime.sqlite3:operations`. Потеря ответа и неподтверждённое обратное чтение дают `ExternalOperationReceipt` со статусом `unknown_outcome`, `requires_reconciliation=true` и `safe_to_retry=false`. Повтор в новом процессе не вызывает провайдера второй раз. Начатый удалённый обработчик может продолжать работу после локального тайм-аута; отсутствие результата поиска не доказывает отсутствия эффекта.

Свежий подтверждённый результат сохраняет прежнюю форму `saved`, `written` или `propagated`. Повтор уже подтверждённой операции возвращает `already_succeeded` со ссылкой `previous_result_receipt_hash`; это исторический результат, `current_readback_verified=false`. Потребитель должен различать эти два новых ответа и не превращать их в новую запись или свежее подтверждение состояния.

Это намеренное ужесточение совместимости. Идентичность памяти определяется областью и хешем содержимого, факта графа — парой `project_id`/`fact_id`. Другой запрос с прежней идентичностью отклоняется как `external_operation_conflict`; новая версия факта требует нового `fact_id`. После начала удаления артефакта новые факты для его `artifact_id` запрещены; новая версия исходного артефакта требует нового `artifact_id`. Прежнее поведение прямого `MERGE`, допускавшее неявное изменение или повторное оживление, не сохраняется.

Операции одного артефакта сериализуются между процессами; ожидание ограничено одной секундой, затем возвращается `graphiti_artifact_busy`. Независимые артефакты используют разные блокировки. Если для артефакта остаётся начатая или неизвестная запись, удаление не вызывается и не подтверждается: возвращается `GraphitiLifecycleReceipt` со статусом `unknown_outcome` и `deletion_observed=null`. Нужна независимая сверка; автоматического снятия этого ограничения по отсутствию поисковой выдачи нет. Старые неизвестные записи без хеша цели также требуют сверки.

Журнал операций хранит только хеш запроса, хеш цели, локальный признак владельца и хеш квитанции. Тексты памяти, фактов и сырые ответы провайдера в него не записываются. Дополнительной базы данных не создано; журнал входит в прежний класс резервирования состояния исполнения.

## Тождественность событий и найденных фрагментов

Повторный `trace_id` принимается только при совпадении полного нормализованного события. Конфликт отклоняется до выборочного исключения события и приёма в очередь. Сверка очереди сохраняет повреждённые и конфликтующие записи для разбора; истечение срока не удаляет их незаметно. Повтор идентичного события остаётся допустимым при заполненной очереди.

Повышение найденного фрагмента проверяет сохранённые хеш записи, хеш содержимого, запуск и состояние. Прежний идентификатор не разрешает повысить изменённый текст или неразрешённого кандидата. Дословное содержимое фрагмента, перенесённое в поля ссылки, версии или координат, очищается существующим механизмом ограничения журналирования; это не проверка произвольных пересказов.

## Граница

Пакет выпускается под Apache-2.0. `foundation_release_verify` для 0.13.0b1 проверяет точный коммит и архив из фиксированного каталога `releases/hermes-foundation-bridge-0.13.0b1`. Открытый ключ входит в пакет; закрытый ключ не входит в исходники, архив и каталог выпуска.

Подписанный выпуск закрывает целостность поставки, но не закрывает G0–G8, не квалифицирует исследовательские профили и не разрешает производственную активацию. Поэтому `production_activation_allowed=false` сохраняется независимо от результата проверки подписи.

`foundation_bridge_migrate` сначала вызывается с `apply=false`. Применение допускается только в новом `HERMES_FOUNDATION_ROOT` либо `<HERMES_HOME>/foundation`. Миграции не читают и не копируют состояние прежнего Hermes.

Создание Beads также предваряется записью в существующем журнале внешних операций. Потерянный ответ запрещает автоматическое повторное создание; возвращается `unknown_outcome` с требованием сверки. Идентичный подтверждённый запрос возвращает `already_succeeded` со ссылкой на прежнюю квитанцию. Для намеренного создания отдельной работы с тем же содержимым передайте новый `operation_key`; повтор ключа с другим содержимым отклоняется. Прежние входы сохраняются, по умолчанию тождественность определяется полным запросом. Потребитель должен обрабатывать `ExternalOperationReceipt`, не ожидать новый `issue_id` у исторического ответа.

То же правило действует для `foundation_beads_claim` и `foundation_beads_close`: повтор после неподтверждённого ответа требует сверки, подтверждённый повтор ссылается на прежнюю квитанцию. `operation_key` различает новые намерения. После ответа CLI назначение проверяется по идентификатору, состоянию и исполнителю, закрытие — по повторно прочитанному состоянию. Ошибка CLI без подтверждённого исхода возвращается как `unknown_outcome`; потребителю нужен обработчик этой квитанции вместо предположения, что исключение означает отсутствие действия.

## Поправка закреплённого Hermes

Новая изолированная поставка использует Hermes 0.21.3, исходный коммит из `bridge-lock.json`, и включённую поправку `patches/hermes-0.21.3-telegram-callback-auth.patch`. Она добавляет общую проверку полномочий до обработки любой кнопки Telegram. Исходный файл, исправленный файл и сама поправка закреплены отдельными SHA-256 в `hermes.patches`.

В новой копии исходников сначала проверьте исходный хеш, затем выполните `git apply --check PATH_TO_PATCH` и `git apply PATH_TO_PATCH`, после чего проверьте исправленный хеш. Это составная зависимость: неизменённый исходный коммит без поправки не соответствует данной поставке. Работающий экземпляр не обновляется этим пакетом автоматически.

## Отдельный локальный стенд

До миграции нового основания можно создать закрытый для записи другими пользователями файл `instance-endpoints.json` в его корне: `{"schema_version":1,"prefix":"e2e44","dolt_sql_port":43317}`. Допустим только префикс локального испытания, начинающийся с `e2e`, и отдельный порт на `127.0.0.1`. Без файла сохраняются прежние адреса. Контейнеры получают имена `<prefix>-agentmemory`, `<prefix>-graphiti`, `<prefix>-falkordb`, сеть — `<prefix>-net`. В отдельной сети FalkorDB должен иметь псевдоним `hermes-foundation-falkordb`; рабочий модуль остаётся неизменным. Создавайте новые тома и служебные секреты, проверяйте отсутствие совпадений имён до запуска. Скрипты подготовки и управления Dolt используют этот же файл. Смена адресов уже созданного адаптера отклоняется; существующие манифесты не перезаписываются автоматически.

Вызовы Beads явно закрепляют `BEADS_DIR` за каталогом текущего основания. Значение, унаследованное от родительского проекта, не выбирает другую базу.

## Приём результатов UDR 0.44 / UDR 0.44 intake

Внутренний интерфейс основания `research_session.ResearchSession` получает контекст
через существующие AgentMemory/Graphiti, проверяет канонический контракт,
исполнителя задачи Beads и действующую аренду. `runtime.check_lease` читает аренду
без продления. `research_intake.ResearchIntake` принимает `ResearchHandoffV1` из
карантина, перепроверяет файлы и сохраняет соответствие локальных записей артефактам
через существующие ArtifactService и Dolt. Повтор по тому же содержимому безопасен;
после частичного сбоя принятые артефакты используются при повторе. Полный корпус не
загружается в память одновременно. Ограничение службы артефактов 64 МиБ относится
к отдельному файлу, не к количеству источников.

Это интерфейс существующего доверенного сеанса, не новый инструмент выдачи
полномочий модели. Владелец сеанса создаёт в `kw_core` объект схемы
`ResearchWorkContractV1` с полями `status=active`, `project_id`, `profile_id`,
`host_run_id`, `holder_id`, `bead_id`, `lease_revision`, `memory_scope`.
`memory_scope` содержит `tenant_id`, `project_id`, `profile_id`, `work_kind`.
Модель и передаваемый пакет не назначают себе этот контракт.

Порядок вызовов в существующем управляющем сеансе:

```python
from hermes_foundation_bridge.bridge import services
```

`run_in_host` передаёт полученный контекст через обычное сообщение существующего
Hermes, создаёт рабочую область, принимает завершённый исследовательский пакет и
синхронизирует память/граф. Синхронизируется факт появления черновика и ссылка на
отчёт; неподтверждённые научные тезисы не выдаются за факты. Состояние завершения
хранится в существующем Dolt. При повторе используются прежний пакет и уже
подтверждённые записи служб. Новый агент или собственный цикл модельных вызовов
не создаются. Штатное отложенное подключение инструментов Hermes поддерживается.

Research должен быть установлен вместе с Foundation и доступен этому Python
окружению; в профиле задаётся `research.integration_mode: foundation`. Контракт
работы, владение задачей и аренду оформляет существующий управляющий сеанс.
При подготовке контекста ошибка обязательной службы останавливает запуск до
модельного вызова. Ошибка завершающей синхронизации оставляет сохранённый черновик
для повторного завершения.

Проверка содержимого — не приём доказательства. Запись в Dolt имеет статус
`imported_draft`; разрешения публикации или доставки не выдаются. Квитанция
подготовки сохраняет происхождение полученного контекста, но не заявляет, что
модель фактически его получила. Маршрут проверяется на отдельном стенде со штатным Hermes и реальными службами.
Регистрация происхождения контекста не является содержательной приёмкой доказательства. Эти интерфейсы не включаются автоматически старым подписанным
выпуском Foundation; `bridge-lock.json` старого выпуска не изменён.

The host-only `ResearchSession` and `ResearchIntake` APIs reuse the existing work,
lease, memory, graph, artifact and Dolt adapters. Intake verifies the producer
manifest, stages one file at a time, imports a draft and maps local IDs to artifact
IDs. Retry does not imply evidence acceptance or delivery authorization. The existing host calls `run_in_host` on its own AIAgent; this delivers retrieved
context, imports the saved draft and synchronizes its completion reference to
memory and graph. `complete` retries finalization without another model call.
Qualification applies only to the tested versions and deployment scope; these
changes do not replace an already signed release.
